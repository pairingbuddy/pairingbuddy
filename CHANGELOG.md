## [Unreleased]

- Questions for you can be answered at any time, not only at the pull request: `/pb-answer` lists them by number and `/pb-answer <n> <answer>` records one through `pb human answer`. The answer reaches the next step that starts as guidance; at the next task boundary `pb plan next` asks the session to settle each answer, and an answer that changes work already done adds a `Rework <k> in <unit>` task to the plan, run next, at most 3 per unit before pb asks whether it is a re-plan. `G:publish` asks only the open ones and lists the answered ones with their answers. A new question sends one quiet desktop notice, with no sound or status line, and the band reads `2 questions for you · answer with /pb-answer` (owner: when at the machine in auto mode, an early answer should change direction within minutes, not after hours of work toward the pull request).

- Under auto mode, a reviewer's or agent's doubt no longer stops the run: it goes on the unit's "questions for you" (at most 20 in full, the rest counted), the gate passes by policy and the ledger records it as deferred, not approved. Before the unit's pull request, G:publish asks every question at once under any policy; publish answers them, redo keeps them. The pane and band count them, the report lists them under NEEDS YOU and /pb-plan under the open unit. Failing tests, step failures, caps, [HUMAN] tasks and other stops still stop at once (T4d Task 111: three reviewer doubts at the task-end gate held an overnight run from about 23:00 to 07:30).

- The `/pb-plan` page folds layer by layer, so the whole plan reads at a glance and each part opens for its detail (owner: see where we are, then dig deeper as needed). A tracer folds to its name and tasks done (`T10: Solo port · 2 of 4 done`) and opens to its Goal and Verification lines, then its units; a unit opens to its tasks; a task opens to its full explanation from the plan: Goal, what to build, acceptance criteria, files. The page opens on the path to the task being built, and the unit holding that task reads `open` on the page and in the pane, even before its unit record exists (it read `to do`). The open unit's commits sit in one fold, `31 commits`, folded, instead of a bare `commit 11feffb` row each: inside, newest first, each hash with its subject, grouped under the task whose recorded last commit ends them. The mod reads the subjects with one read-only `git log` over the unit's own commits, as `/pb-report` reads a run's; a failed read shows the bare hashes. Expand all and Collapse all show only where the page's script runs; without it every fold still opens by hand. Plan text is escaped first, then only bold, inline code, paragraphs and lists are read, so no markup from the plan reaches the page.

- A fix rollback removes the untracked files the fix created without listing them, such as the `-e` backup `sed -i -e` leaves on macOS, and keeps them under a rollback ref; untracked files that were there when the stage's snapshot ran are never touched and no longer block the rollback (T4d Task 111: a fixer's `cli/pb.mjs-e` made the rollback refuse with "the tree is dirty outside the fix group", and the run stopped). `pb snapshot` records those files in the ledger's `fixes.untrackedAtStart`, up to 1000; past that nothing is recorded and a rollback refuses over untracked files as before. Safety-net fixers are told to edit with the Edit tool, never `sed -i`.

- The band's commands hint reads `details: /pb · report: /pb-report · plan: /pb-plan`, each command after its label, and names `/pb-plan` (live T4d: `/pb details · /pb-report report` read as typing `/pb details`). A narrow band drops whole commands from the right, plan first, then report, never one cut mid-word; the short `/pb · /pb-report` form is gone.

- An unfinished Solo run can no longer look finished (Task 112): when `claude -p` exits 0 but the ledger holds a stop, a human gate still waiting or a stage still active, `solo-buddy.sh` prints `Session stopped`/`Session unfinished`, shows the failure footer and exits 1. A stop at the attempt cap lists its attempts and the first lesson line of each rollback in the stage's notes, and the exit summary lists every `PR: <url> branch: <name>` link from the plan MD. Smoke S9 (`tests/smoke/s9.mjs`, run by hand within a $6 cap) drives Solo on a two-unit plan on the recording `gh` shim, and asserts two draft PRs, the report, and that a forced stop leaves its commits local.

- Solo's script no longer pushes or opens pull requests (Task 111): the `git push` and `gh pr create` steps are gone from `solo-buddy.sh`, and the publish stages own both. Every Solo PR opens as a draft, and a failed publish is retried once before the run stops. A stop pushes nothing, and units already published stand. `SOLO_BUDDY_REPORT.md` is no longer a PR body, the exit summary has no PR lines, and `test_solo_buddy_pr_creation.py` is retired. The other Solo test files stay until T12.

- Every unticked `[HUMAN]` task in the pane's PLAN block and on the `/pb-plan` page is lit in the needs-you colour and reads `needs a person`; `waiting on a person` is kept for the one the plan has reached, its first unticked task (live /pb-plan: of T13's four person's tasks only Task 135 was lit, as its unit's next, though the run was still on T10).

- No task ends and no pull request starts on code that fails the project's lint: test-config.json takes optional `lint_commands` (check-only, such as `ruff check .` and `ruff format --check .`), and every full suite runs them after the tests, so a lint failure fails the suite like a failing test. The fix loop rolls the fix back with the lint's output, a checkpoint refuses the commit, and publish finds no green suite. With none set, the full run records "no lint configured" and the task-end question shows a `Lint:` line, naming `.pre-commit-config.yaml` or `.husky/pre-commit` when the repo has one; the hook is named, never run, as a hook may fix files in place. The setup step fills `lint_commands` from the commit hook or CLAUDE.md (T4d Task 110: ruff ran only in the commit hook, so a fix with a long line got to the commit before anyone checked it).

- A PR draft whose lint fails is redrafted instead of stopping the stage: a failing lint verdict counts whatever exit code the runner relays, and each finding gives the redraft the failing body line and the lint's remedy. The drafter is told the lint's rules up front, `.pairingbuddy/` paths among them (T10a pr-draft: the runner relayed exit 1 with the lint's failing verdict on a `.pairingbuddy/` line, and the stage stopped step-failed with no redraft).

- Solo's terminal renderer reads the new state (Task 110): the unit's branch and task count from `run/unit.json`, run progress from the ledger, the latest `task_progress` description and spend summed from `task_notification` usage in the stream. `claude -p` runs with `--output-format stream-json --verbose`, stdout captured to `.pairingbuddy/solo-stream.jsonl`. A missing, empty or malformed file does not crash the renderer, and text it shows is bounded and sanitized.
- Solo enters the new workflows (Task 109): `solo-buddy.sh` sets `PAIRINGBUDDY_GATE_POLICY=auto`, read only by hooks, and starts `/pairingbuddy:code` on the plan, which runs the Plan Loop (`pb plan next`, `pb task end`, again) as outside Solo. The T7b router check is lifted. Caffeinate, the branch guard (no start on main or master) and API key handling are unchanged, and a `[HUMAN]` task stops the run with a clear message.

- A safety-net fix whose commit the repo's commit hook refuses is rolled back like a fix that fails the suite: nothing stays staged, it counts toward the 5-attempt cap, and the next fixer is told the hook's output. Fixers are told to run the lint and format checks the hook runs before they finish (T4d Task 110: a ruff line-too-long in a test docstring stopped the whole stage with "the commit failed" and left the change staged).

- Accepting a changed test-config.json in the session, as well as with `pb human accept`, pins it in the open unit too, so `pb publish` does not refuse it later (the tap's Accept updated only the run's ledger).

- A refused stage start says the running stage "is still running" and, when stuck, that the human clears it with pb stage fail, instead of "is active at attempt N" (T4d: the refusal read as jargon). A stage with no recorded run says to start it again, with no attempt number.

- A safety-net fixer is told that the full suite must pass after its fix, so a fix that rewords text tests check word for word updates those tests in the same fix, keeping what they check (T4d Task 109: five fixes reworded the coding skill, broke the router tests that pin its wording, were all rolled back, and the run stopped at its cap of 5).

- A gate answered with typed words instead of a listed choice sends its step back with the words as the note, the way redo with a note does; typed words never approve. A question with no redo (go on, a changed config) keeps waiting, and the session is told only a listed choice counts (T4d G:scenarios: a typed answer to a reviewer's doubt was dropped, and the same question came back with no word why).

- The PLAN window centres on the unit whose pull request is being written, or not opened yet, instead of the next unticked task (live at 20 and 30 rows the unit being published had dropped out of view). In a short pane the details also fold while PLAN would get fewer than 12 rows; TESTS only once the build is over, and REVIEW first once the work is finished, as the report holds its findings. A short PLAN block shows the open unit's commits on two rows.

- The pane fits the rows the terminal gives it, so PLAN shows without scrolling (live: PLAN sat under STEPS, TESTS and REVIEW, below a 20 to 45-row window, with no hint it was there). In a short pane STEPS folds to one line (`✓ 4 done · ▸ write the pull request`), then TESTS to its count and the running test, then REVIEW to its summary, until PLAN has at least 7 rows; PLAN gets the rest, up to 24. A pane still too tall ends its window with `↓ 12 more rows · ctrl+x tab, then arrows`. The pane lists at most three labels pb could not read, the latest, under their count.

- `pb publish` publishes after the human accepts a changed test-config.json during the unit's code run (T4d publish: it refused with `these files changed since the unit opened: test-config.json`, and no command could clear it, since the acceptance was only in the code run's ledger and that run had ended). Publish now takes the hash accepted in one of the unit's own kept runs, and `pb human accept` with a unit open pins the new hash in `unit.json` too.

- Once the build is over, TESTS shows a covered test as passing: `✓ poll picks up plan change · covered` (T4d publish run: under `✓ 17 of 17 passing · 8 covered`, its `◌` read as not started).

- SPENT and the report's Spent leave out any gap of more than an hour between two ledger writes (T4d run: SPENT read 22:52:56 for a couple of hours of work, as the code run's overnight stop and the stops between sessions came before stops were stamped). Every step, test run and owner's tool call writes the ledger, so nothing ran then; the write that ends the gap keeps it in the ledger's `idleWaits`.

## [0.8.0-exp.2] - 2026-11-23

- The runner runs its own commands whatever a relayed user request says. The Claude Code workflow harness hands every workflow agent the human's last message, marked as overriding the computed task; in the T4d run that message said to clear the stage with `pb stage fail`, and the fix's checkpoint runner ran that. `agents/runner.md` now says that request is the human talking to the main session about the run as a whole, never changes which commands the runner runs, and that a runner whose commands seem to conflict with it runs them anyway and looks for no others.
- A runner relay that shows pb never answered is a broken relay, not a failed step (live T4d run: the harness relayed the human's "clear it with pb stage fail" to the fix's checkpoint runner, which ran that instead, was blocked, and returned exit 1 "not run", so the safety net counted a failed fix). A relay with no `pb: ` line and no JSON from pb runs its runner once more under a key of its own: no fix attempt is spent and nothing is rolled back; broken twice, the loop ends with step-failed. code-tdd runs such a runner again as it does a lost one. A code-mode fix attempt now reserves 5 agents of the budget, for that re-run.
- The guardian and solo-progress hooks read their payload from fd 0, not by opening `/dev/stdin`, which fails with ENXIO on Linux when a Node parent spawns the hook with piped stdio. A test spawns each hook with piped stdin, and another checks that no shipped script opens `/dev/stdin` by path.
- A stage whose workflow died in a live session reads `▲ NEEDS YOU · restart the step: its workflow ended without finishing`, not `take over the run: its session is gone` (live T4d run: the safety net's workflow threw, the session was alive, and the pane offered `pb human adopt`). When this session ran agents of the active stage and none still runs, the session is the one showing the pane, so only the workflow ended. STATUS gives the way on under it: `tell Claude to restart it: pb stage fail, then pb status --action`. A stage no agent of this session ran keeps the take-over line.
- A relayed `pb snapshot` reads even with text around its JSON (live T4d run: the runner put `$ node .../pb.mjs snapshot` in front of the JSON, and the safety net threw `pb snapshot gave no corpus (exit 0)`). Every stage reads relayed CLI output the one way, from the first `{` to the last `}`. The runner is told that `cli_output` holds only what the commands printed, with no command line, `$` prompt or words of its own.
- A selected run that ran no test no longer counts as a pass. `node --test --test-name-pattern=^nothing$ file` exits 0, counting the file itself as one passing test, so pb now needs the test named as passing in a node runner's output (`✔ name` or `ok N - name`). Otherwise GREEN, a later RED and GREEN's and REFACTOR's check of the earlier tests refuse, saying the test `ran no test: its selector matched none`. pytest's exit 5 is told as `collected no test`, and the mod helper already exits 1. Test runs no longer inherit `NODE_TEST_CONTEXT`, so a pb started under `node --test` still sees a node runner's own report.
- A full-suite run of a `node --test` runner names the files its `file_pattern` matches, not the bare test folder (live T4d run: `node --test tests/js` on Node 25 ran every `.mjs` there, helper shims that wait on stdin included, so the safety net's check hung past its 540s timeout every time). pytest and the other runners keep the folder. A run that timed out says so by name in the refusal: `runner js timed out after 540s`, or `test t9 (...) timed out after 10s`.
- Text a person reads says "you", not "the human": `pb status` at a terminal (a stop reads `you answered stop at G:task-end`) and a gate question's why line when it carries a raw reason. The pane, the band and the questions already did. Text only the model reads keeps "the human", so the model never takes "you" as itself; `forYou` in `shared-node/plain-names.mjs` turns one into the other.
- Time a run sat stopped is left out of SPENT for good, not only while the stop stands (live T4d run: SPENT read `2:06:13 paused` at a stop near 00:22, the human went on near 10:00, and at the next stop SPENT read `14:22:03` for about four hours of work). Every ledger write that sets a stop opens a wait in the new `stopWaits` list and the write that lifts it closes it. SPENT, the TESTS step age and the report's Spent leave those waits out as they do questions and permission prompts, and a question asked while the run is stopped counts once. Ledgers written before this have no stop waits, so a past stop still counts.
- `claude plugin test .` no longer dirties the tree for `pb unit open` (live run: it left an untracked `node_modules/.vite/`). This repo ignores `node_modules/`, and `cli/mod-test-one.mjs` removes a Vite cache its run made, and a `node_modules` it made that holds nothing else; one that was there before stays. pb's dirty-tree check is unchanged.
- The TESTS row's step age stops where the run stopped or started waiting on the human, as SPENT's time does (live T4d run: `REFACTOR 9:57:19` kept counting through a stop while SPENT said paused).
- GREEN's commit check also runs every test an earlier cycle closed, as the per-cycle refactor's does (live T4d run: GREEN for one test broke an earlier one, its check ran only its own test, and the regression was found only at the next REFACTOR). A broken earlier test is refused at GREEN, named with its output, so implement-code fixes it in its next try; the run lands in `ledger.tests.closed`. implement-code is told to fix its code so both pass, and to change an earlier test only when the task itself requires behaviour that test contradicts, saying which and why in `notes`.
- A refused commit check names what failed (live T4d run: REFACTOR was refused three times with only `exit codes 0, 0, 0, 0, 0, 1, 0, 0, 0`, the agents guessed wrong, and the stage stopped after two hours). The per-cycle check names each failing test by id, function and file, with its exit code and the last 1500 characters of its output; the full-suite check does the same per runner. The refusal is what the stage's next try gets as `previous_refusal`.
- A config change with no `config_globs` gets the human's OK through a question, not a typed `!pb human approve-config` line. `pb task end` refuses as before and sets the run waiting (`needsHuman` gate `config-approval`, `Confirm` or `Not now`); the session asks it, and the tap records Confirm as `configApproval: {source: "human"}`, so the next `pb task end` passes. The `!` line stays as the fallback.
- A human's stop at a gate is lifted by a question, not a typed `!pb human approve <gate>` line. Once they say they want to go on, `pb gate eval` stores a go-on question (`Go on` or `Stay stopped`, marked `needsHuman.wait: go-on`), the session asks it with AskUserQuestion, and the tap records the human's answer: Go on approves the gate as theirs and lifts the stop. The approve line stays as the fallback, and the gate's deny says the same.
- A changed test-config is asked as a question, not a `!` line to type (human: "The UX is weird when you need to start running commands with escape"). The wait stores its question (`Accept` or `Stop`); `pb status --action` tells the session to ask it with AskUserQuestion, and the tap records the human's answer as it does a gate's: Accept pins the file and the stage starts again, Stop is the human's stop. The model never records it. The pane's line under the wait reads `answer the question in the session, or type !.pairingbuddy/bin/pb human accept`, the fallback when no question can be asked.
- A dirty tree is named before the human is asked anything (live run: `pb unit open` refused on untracked files only after curating-guidance had asked the human). With no run and no unit open, `pb status --action` lists the `dirty` files and says to show them and stop, and the coding skill does so before any question.
